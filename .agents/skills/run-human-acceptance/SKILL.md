# Run Human Acceptance

1. Read `docs/acceptance/HUMAN-ACCEPTANCE-TEST-PLAN.md`. Treat its version, scenario text, availability, expectations, pass criteria, and severity rules as canonical; never invent or silently weaken them.
2. Preflight the platform, Node version, repository checkpoint, disposable synthetic workspace, access route, and local evidence/checkpoint locations. Run all machine-verifiable checks yourself and report them separately. Never ask the human to inspect developer tools, schemas, logs, JSON, source, commands, digests, isolation, or protocol behavior. Stop if real learner data, identity, raw chat, secrets, deployment, or an unauthorized external write is in scope.
3. Initialize or validate the local checkpoint with `scripts/checkpoint.py`. Bind its plan digest/version, exact product commit, and a recognized `test_only` workspace manifest without storing its path. On resume, confirm those still match before continuing.
4. Select only a runnable human-visible scenario unless the human chooses to record a gated scenario as `blocked` or `skipped`. Do not substitute command output or unit behavior for a missing product surface. State the scenario purpose, setup, and rollback, then present exactly one numbered human action with its expected experience.
5. Accept free-form feedback immediately, even during an active action. Acknowledge it, sanitize it into a concise privacy-safe item, and record it with `checkpoint.py feedback`; do not force it into an observation or verdict. Then return to the current action. Ask what the human observed and record only an allowed observation category plus an optional privacy-safe artifact reference; never store raw chat.
6. Ask the human whether the observation matched the expectation stated before the action. Record their action outcome, then continue one action at a time. The agent may identify a discrepancy but must not assign an action outcome or scenario verdict.
7. At scenario end, show the canonical pass criteria and default failure severity. Accept only the human's `pass`, `fail`, `blocked`, or `skipped` verdict and chosen severity. Never infer a pass from logs, waive a failure, or change a verdict.
8. Pause immediately on request and persist the next action. Resume only after confirming the checkpoint, plan digest, disposable root, and product checkpoint. Use the plan's reset instructions; delete only a checkpoint whose exact run ID the human confirms.
9. At run end, show the complete feedback register, consolidate only with human approval, and let the human mark items non-actionable. For every approved actionable item, use `$add-zzzops-goal` and preserve its scenario/action, desired user outcome, observable acceptance evidence, and constraints. Create those goals before the release summary.
10. Summarize automated prerequisites separately from human verdicts, including counts, blocking failures, unavailable/unobserved coverage, privacy-safe artifacts, and feedback-to-goal results. Ask the human to approve or correct the summary and assign `go`, `no-go`, or `conditional`; never make that release decision yourself.

Use `python .agents/skills/run-human-acceptance/scripts/checkpoint.py --help` for deterministic commands. Pass `--assigned-by human` wherever required; this is an integrity assertion based on the current human message, never an agent default.
