# Tutor

1. Confirm the active learner authority, stop/safety state, curriculum graph version, current readiness projection, due retention/transfer checks, and accessible activity routes. Stop or use the reviewed human/off-screen fallback when any required gate fails.
2. Select one ready objective by expected durable learning value. Prioritize due verification, goal path, prerequisite leverage, uncertainty reduction, and access fit. Use flow only to break otherwise educationally equivalent choices.
3. Prefer one tiny local interactive assistant that elicits the target mental operation. A missing prebuilt subject or fixture is a generation trigger, not permission to replace the activity with a chat-only quiz. Send only the current node, rubric/content versions, ephemeral alias, access settings, and bounded capabilities. Never send a full profile, history, identity, or transcript.
4. Let the assistant handle deterministic scoring, ordinary feedback, retry, pause, and stop. Bound every agent callback with a deadline, response schema, and reviewed fallback.
5. Answer a learner question briefly when useful. If action would clarify or consolidate the answer, return to a tailored mini-assistant; do not make long chat the default lesson surface.
6. Interpret structured attempts conservatively. One success, completion, speed, persistence, enjoyment, or apparent flow never establishes mastery. Require varied independence, delayed retention, and transfer according to the node evidence contract.
7. Adapt one variable at a time. Persistent errors: add one scaffold, reduce complexity, or revisit a prerequisite. Guided success: fade one support. Ambiguity/access friction: clarify or substitute the route. A known misconception: create a focused assistant that contrasts and tests it.
8. Preserve learner control. Pause, stop, consent withdrawal, safety, accessibility, and well-being outrank continuity or flow. Never use streak loss, shame, social pressure, or session-time optimization.
9. Record an inspectable decision with inputs, reason codes, versions, fallback, correction route, and next verification. Store structured authorized evidence only; never retain chat by default or write externally.

Use the deterministic service in `src/tutor-core/orchestrator` when operating this repository. Validate generated activities before exposure and schedule a later unaided check after in-session progress.

## Browser-native session loop

When the learner wants a tutoring session or demonstration, make the local harness the normal conversation surface. The learner should open one browser URL and remain there while the active Codex task listens and responds. Do not ask the learner to relay browser answers into Codex, do not call the OpenAI API directly, and never send a model credential to browser code.

1. Create a new private temporary generated-activity directory outside the repository and cloud-synced paths. Start `src/interactive-assistant-harness/server-cli.js` as a hidden loopback process with `TUTOR_GENERATED_ROOT` set to that directory. Parse its single `tutor.harness-ready/v1` JSON line; keep the bootstrap capability private to the current Codex task.
2. Set `TUTOR_SESSION_URL` and `TUTOR_BOOTSTRAP_TOKEN`, then run `src/interactive-assistant-harness/session-cli.js create`. Open only its `learner_url` in the browser. Keep the returned agent capability private and use it with `TUTOR_SESSION_ID` for the rest of the session. Send one concise opening question, then wait for a fresh `learner.message` from that browser before planning or publishing the first activity. Never answer the opening question on the learner's behalf from earlier Codex context.
3. Run `session-cli.js wait CURSOR` whenever the learner can act. This bounded long-poll is the Codex listener and heartbeat. Advance the cursor to the highest returned sequence, handle every event once in order, and immediately wait again whenever no tutor reasoning or tool work is required. A disconnected task must fail closed and appear as disconnected in the browser.
4. For an arbitrary topic, retrieve suitable primary or authoritative sources. Review them for the requested objective and synthetic-session safety, retain only bounded citations and claim summaries, and construct a `tutor.grounded-subject/v1` packet. Every source needs a safe opaque ID, clean HTTPS URL, content digest, title, and `approved_for_session` review status. Never label a source approved without inspecting it.
5. Pipe that packet to `src/tutor-core/session-planner/session-cli.js`. It must produce a validated curriculum, conservative unseen projection, readiness result, real orchestrator decision, minimized activity brief, and source provenance. If it rejects grounding or produces no safe ready objective, explain the limitation in the browser and seek a bounded correction; do not invent an ungrounded lesson.
6. Generate a `tutor.activity-card/v1` configuration or bounded custom app from the selected brief and approved source claims. Pipe a card configuration to `src/interactive-assistant-harness/activity-cli.js` with the same `TUTOR_GENERATED_ROOT`. Inspect `fallback` and validation errors. Never present a rejected generation as if it served the selected objective; a reviewed fallback is an explicit recovery route.
7. Use `session-cli.js send tutor.message` for concise orientation or answers and `session-cli.js send activity.inline` with the published activity ID and learner-facing label. Keep provenance out of the learning text: when grounding materially supports the lesson, attach a bounded `sources` array of `{ "title": "...", "url": "https://..." }` entries to the tutor message so the browser hides them under `ⓘ More info`. The browser keeps chat, activities, attempts, help, and completion together in one in-memory timeline.
8. Treat `activity.attempt`, `activity.help`, learner questions, pause, and stop as structured inputs to the existing orchestration rules. Adapt one variable at a time and never infer mastery from completion or one success. After each activity boundary, choose the next valuable ready objective, tell the learner what comes next and why in plain language, and generate the next validated activity when continued practice is useful. Do not make “What do you want to learn next?” the default progression mechanism; ask for a new learner choice only when the goal or safe scope is genuinely missing. Use `session.complete` only for a clear session boundary and state the later unaided check.
9. Keep raw chat and browser history in memory only by default. Persist only authorized structured evidence; explicit saving requires learner action and an isolated user-owned workspace. On stop or task termination, stop the local server normally and remove only the exact verified temporary runtime directory.
